# NestJS Production Test Stand Design

**Status:** Approved design direction; implementation plan follows user review.

**Goal:** Build a separate, local-only NestJS 11 application that exercises Wotchi against PostgreSQL, Redis, scheduled worker failures, HTTP failures, Docker Compose services, and a future Render deployment shape.

**Scope boundary:** This is a disposable validation fixture, not a Wotchi runtime service, hosted collector, production database, or release artifact. It must remain outside the root SDK dependency graph and package archive. The current `.test_stands/` directory is ignored; actual Render deployment is a later, explicitly approved step.

## Architecture

The stand lives at `.test_stands/nest-production/` and runs as one NestJS 11 process. It creates a Wotchi client with the console notifier enabled by default and an optional HTTPS webhook notifier configured only from environment variables. PostgreSQL is accessed through Prisma and Redis through `ioredis`; both are fixture-only dependencies.

The application exposes liveness, readiness, dependency checks, deterministic failure triggers, and a deterministic notifier test. A scheduled probe service uses built-in Node timers rather than adding `@nestjs/schedule`. Each tick performs bounded PostgreSQL and Redis checks. When failure injection is enabled, the service optionally injects an application, PostgreSQL, or Redis failure (or rotates between them), catches it at the worker boundary, and calls `wotchi.captureException` with safe job/dependency context. The scheduler never changes host process retry or shutdown semantics.

## Components and files

- `.test_stands/nest-production/package.json` — private fixture dependencies and start/schema commands; no root package changes.
- `.test_stands/nest-production/package-lock.json` — fixture lockfile generated by the approved install command.
- `.test_stands/nest-production/tsconfig.json` — strict TypeScript compilation for the stand.
- `.test_stands/nest-production/.env.example` — safe local defaults and opt-in failure controls; no credentials.
- `.test_stands/nest-production/docker-compose.yml` — PostgreSQL 16 and Redis 7 with isolated host ports and health checks.
- `.test_stands/nest-production/prisma/schema.prisma` — one bounded heartbeat/probe state record used to prove database writes.
- `.test_stands/nest-production/src/main.ts` — Nest bootstrap, Wotchi registration, notifier configuration, and graceful shutdown.
- `.test_stands/nest-production/src/app.module.ts` — controller/service/provider composition.
- `.test_stands/nest-production/src/app.controller.ts` — health, readiness, dependency, trigger, and test-alert routes.
- `.test_stands/nest-production/src/runtime-services.ts` — Prisma/Redis initialization, status, safe close, and dependency helpers.
- `.test_stands/nest-production/src/scheduled-probe.service.ts` — timer lifecycle, healthy probes, opt-in failure injection, and worker-boundary capture.
- `.test_stands/nest-production/README.md` — local Docker workflow, curl smoke commands, configuration, security limits, and later Render preparation notes.

The existing `.test_stands/nest-v11` fixture and root SDK sources are not modified by this stand.

## Configuration

The stand uses these defaults:

| Variable                     | Default                         | Purpose                                                                     |
| ---------------------------- | ------------------------------- | --------------------------------------------------------------------------- |
| `HOST`                       | `127.0.0.1`                     | Local bind address.                                                         |
| `PORT`                       | `3011`                          | Stand HTTP port.                                                            |
| `DATABASE_URL`               | PostgreSQL on host port `55432` | Fixture database connection.                                                |
| `REDIS_URL`                  | Redis on host port `56381`      | Fixture cache connection.                                                   |
| `REQUIRE_TEST_SERVICES`      | `true`                          | Fail startup when either dependency is unavailable.                         |
| `WOTCHI_FAILURE_INJECTION`   | `false`                         | Opt in to scheduled random failures.                                        |
| `WOTCHI_FAILURE_INTERVAL_MS` | `30000`                         | Scheduled probe interval; validated as a bounded positive integer.          |
| `WOTCHI_FAILURE_RATE`        | `0.25`                          | Probability of an injected failure per tick; validated between `0` and `1`. |
| `WOTCHI_FAILURE_KIND`        | `rotate`                        | `app`, `postgres`, `redis`, or `rotate`.                                    |
| `WOTCHI_STAND_TOKEN`         | empty                           | Optional token for trigger and notifier-test routes.                        |
| `WOTCHI_WEBHOOK_URL`         | empty                           | Optional HTTPS webhook destination.                                         |
| `WOTCHI_WEBHOOK_AUTH`        | empty                           | Optional authorization header value, never stored in source.                |

Failure injection is disabled by default. Manual trigger routes remain deterministic and are intended for local smoke testing. If `WOTCHI_STAND_TOKEN` is set, trigger and test-alert routes require the `x-wotchi-stand-token` header; public deployment must set it.

## Data flow

```text
HTTP trigger or scheduled probe
  -> dependency/application operation
  -> catch at Nest filter or scheduled worker boundary
  -> Wotchi normalize + redact + fingerprint + group + threshold/cooldown
  -> bounded console or optional HTTPS webhook notifier
```

The healthy scheduled path upserts one heartbeat row and writes one short-lived Redis key. It does not retain unbounded event history. The failure path uses fixed safe context fields such as `job`, `dependency`, and `trigger`; it never sends request bodies, credentials, or full environment values to Wotchi.

## Failure and shutdown behavior

- `/healthz` is dependency-independent and returns `200` while the process is alive.
- `/readyz` verifies PostgreSQL and Redis and returns `503` if either is unavailable.
- Dependency initialization records a sanitized status and fails startup when `REQUIRE_TEST_SERVICES=true`.
- HTTP trigger errors pass through the normal NestJS exception filter; Wotchi observes them without taking response ownership.
- Scheduled errors are caught, captured with Wotchi, and do not terminate the scheduler or host process.
- Notifier failures remain isolated by Wotchi's bounded queue.
- `SIGINT` and `SIGTERM` stop the timer, close Nest, disconnect Prisma and Redis, and flush pending Wotchi work within a bounded timeout.

## Docker and future Render boundary

`docker compose up -d --wait` starts only the local PostgreSQL and Redis fixtures. The README documents `docker compose down` and volume-reset commands. The stand does not include production credentials or a hosted notifier token.

The first implementation documents how to build/run the stand for a later Render experiment but does not deploy it, configure Render resources, or publish ignored `.test_stands` files. A Render deployment requires a later decision about whether to use a released Wotchi package or an explicitly checked-in deployment fixture.

## Verification

Implementation verification must cover:

1. TypeScript compilation and formatting of the stand source.
2. Docker Compose health for PostgreSQL and Redis.
3. `/healthz` succeeds without dependency calls.
4. `/readyz`, `/db-check`, and `/redis-check` succeed with both services healthy.
5. Deterministic application, PostgreSQL, and Redis trigger routes return errors while producing grouped Wotchi console alerts.
6. The scheduled service remains quiet with failure injection disabled.
7. With injection enabled and `WOTCHI_FAILURE_RATE=1`, scheduled failures are captured without process exit.
8. `/test-alert` sends one deterministic notifier message.
9. Trigger routes reject missing or incorrect `x-wotchi-stand-token` when configured.
10. Graceful shutdown closes services and stops further scheduled work.

Root SDK checks remain the source of truth for Wotchi changes. The stand's Prisma, Redis, Docker, and Nest dependencies must never be added to the root `package.json`, root lockfile, published archive, or SDK production architecture.
